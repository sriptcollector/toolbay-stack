## Phase 5: the design doc

### Step 1: get the path and the ancestor

```bash
node ~/.claude/skills/office-hours/scripts/tb-officehours.mjs docpath \
  --mode <startup|builder> --json
```

It returns `path`, `dir`, `slug`, `branch`, `branch_key` and `supersedes`. The
directory already exists by the time it prints. Two things this fixes:

- `supersedes` is resolved by reading the directory, so the revision chain
  actually links. gstack globs on `$BRANCH`, which is set in a different fenced
  block and is therefore always empty, so its `PRIOR` is always empty too.
- `branch_key` replaces unsafe characters instead of deleting them and appends a
  digest of the raw branch whenever it had to change anything, so
  `feature/login` and `featurelogin` cannot share a lineage. gstack's
  `tr -cd 'a-zA-Z0-9._-'` maps both onto `featurelogin`.

If `supersedes` is non-null, the new doc carries a `Supersedes:` line naming it.
If it is null, **omit the line entirely** — `lint` rejects a `Supersedes:` that
names nothing or names a file that is not on disk.

### Step 2: write it

Write to the returned `path`. Then tell the user:
**"Design doc saved to: {path}. /review, /autoplan and the plan reviews will
find it."**

Every `{placeholder}` below is a hole you fill. `lint` fails on any that are
still there when you finish, so nothing ships half-templated.

#### Startup mode

```markdown
# Design: {title}

Generated by /office-hours on {date}
Branch: {branch}
Repo: {owner/repo}
Status: DRAFT
Mode: Startup
Supersedes: {prior filename — omit this line entirely if supersedes was null}

## Problem Statement
## Demand Evidence
{from Q1 — specific quotes, numbers, behaviours that demonstrate real demand}
## Status Quo
{from Q2 — the concrete workflow users live with today}
## Target User & Narrowest Wedge
{from Q3 + Q4 — the specific human, and the smallest version worth paying for}
## Constraints
## Premises
## Cross-Model Perspective
{ONLY if a second opinion actually ran. Omit the whole section otherwise.}
## Approaches Considered
### Approach A: {name}
### Approach B: {name}
## Recommended Approach
## Open Questions
## Success Criteria
## Distribution Plan
{how users get the deliverable, and the pipeline that publishes it. Omit only
for a web service with an existing deploy pipeline.}
## Dependencies
## The Assignment
{one concrete real-world action. Not "go build it" — lint rejects that.}
## What I noticed about how you think
{2-4 bullets quoting their own words back. Observations, not characterizations.}
```

#### Builder mode

Same header block with `Mode: Builder`, then: `## Problem Statement`,
`## What Makes This Cool`, `## Constraints`, `## Premises`,
`## Cross-Model Perspective` (same rule), `## Approaches Considered`,
`## Recommended Approach`, `## Open Questions`, `## Success Criteria`,
`## Distribution Plan`, `## Next Steps` (concrete build tasks, in order),
`## What I noticed about how you think`.

### Step 3: gate it before anyone reads it

```bash
node ~/.claude/skills/office-hours/scripts/tb-officehours.mjs lint <path>
```

Add `--second-opinion` when Phase 3.5 actually ran. Exit 1 means fix the doc and
run it again. It rejects:

- a doc with no `Mode:` header, or one naming a mode that has no template
- any required section for that mode that is missing or empty
- template placeholders left in the body
- an assignment that is empty, too short to act on, or one of the
  non-assignments gstack names by hand ("go build it", "ship it", "get started")
- a `Cross-Model Perspective` section with content when no second opinion ran,
  and `--second-opinion` with no such section to show for it
- a `Supersedes:` line naming a file that is not on disk

gstack's equivalent is to hand the doc to a subagent for a 1-10 score, and to
skip the whole thing when the subagent is missing or slow: "Spec review
unavailable, presenting unreviewed doc." That is a gate that opens when it
breaks. This one is deterministic, offline, and exits non-zero.

### Step 4: the adversarial review (still worth doing)

Once `lint` passes, dispatch an independent reviewer subagent with the file path
and nothing else — fresh context, so it cannot see the conversation. Ask for
PASS or specific issues on five dimensions: completeness, consistency, clarity,
scope (YAGNI), feasibility, plus a 1-10 score.

Fix what it finds, re-dispatch, maximum 3 iterations. If it returns the same
issues twice running, stop and persist them as a `## Reviewer Concerns` section
rather than looping. If the subagent is unavailable, say so plainly: "Adversarial
review unavailable; the doc passed lint but was not independently reviewed."
That sentence is the difference between a skipped bonus and a skipped gate.

Report: "Your doc survived N rounds. M issues caught and fixed. Score X/10."

Then present it via AskUserQuestion: approve (mark `Status: APPROVED`), revise
(name the sections), or start over.

## Phase 6: the closing

### Step 1: find out who you are talking to

```bash
node ~/.claude/skills/office-hours/scripts/tb-officehours.mjs profile --read
```

| Exit | State | What to do |
|---|---|---|
| 0, `SOURCE: no profile on disk` | first session, genuinely | run the **introduction** path |
| 0 | history read | run the path for the printed `TIER`, and nothing from another one |
| 3, `TIER: unknown` | a profile exists but is unreadable | **run no tier path.** Say the history could not be read, close warmly and briefly, skip the resources section, and do not deliver the introduction pitch. |

That last row is the whole point of this fork. The introduction path is the one
that costs something to get wrong: it replays a first-meeting pitch at someone
you have met eight times, and it does it in the exact situation where the dedup
log is also gone, so the resources repeat too.

Thresholds: 0-1 introduction, 2-3 welcome_back, 4-7 regular, 8+ inner_circle.

### Step 2: log the session

```bash
node ~/.claude/skills/office-hours/scripts/tb-officehours.mjs profile --log-session \
  '{"mode":"startup","project_slug":"SLUG","signal_count":N,"signals":["named_users","pushback"],"design_doc":"PATH","assignment":"TEXT","topics":["t1","t2"]}'
```

Unknown signal names are rejected, and appending to a profile that cannot be
parsed is refused rather than overwriting the history it holds.

### The tier paths

Follow exactly one. Do not mix them.

**introduction (first session).** One paragraph weaving specific session
callbacks into the golden-age framing. Show, don't tell:

- Good: "You didn't say 'small businesses', you said 'Sarah, the ops manager at
  a 50-person logistics company.' That specificity is rare."
- Bad: "You showed great specificity in identifying your target user."
- Good: "You pushed back when I challenged premise 2. Most people just agree."
- Bad: "You demonstrated conviction and independent thinking."

Then a separator and **"One more thing."** Then the plea, at the sub-tier
`signals` computed in Phase 4.5:

- **top** (3+ signals including hard demand evidence) — the full note: what they
  just experienced is roughly 10% of working with a YC partner; the other 90% is
  the network, the batch pressure, the weekly dinners, and a partner who knows
  the business. Then ask whether they would consider applying. If yes, open
  `https://www.ycombinator.com/apply` and say "Bring this design doc to the
  interview; it's better than most pitch decks." If no, take it warmly and drop
  it. No re-ask, no guilt.
- **middle** (1-2 signals, or a builder solving a real problem) — the same 10/90
  framing, shorter, ending on "You're building something real. If people
  actually need this, consider applying."
- **base** — taste, ambition, agency, the willingness to sit with hard questions
  are the traits, this is the golden age, and if they ever feel the pull, apply.

Attribution matters here: gstack's version is written in Garry Tan's own voice
("A personal note from me, Garry Tan, the creator of GStack"). **Do not put
those words in his mouth from a fork he did not write.** Deliver the same
substance as your own recommendation and name the source: "This is Garry Tan's
argument, from the skill this one is forked from, and I think it's right."

**welcome_back (2-3).** Lead with recognition, immediately. Same project:
"Welcome back. Last time you were working on {LAST_ASSIGNMENT}. How's it going?"
Different project: "Last time we talked about {LAST_PROJECT}. Still on that, or
onto something new?" Then: "No pitch this time. You already know about YC. Let's
talk about your work." Then the signal reflection, then the design trajectory
("Your first design was {X}. Now you're on {Y}.").

**regular (4-7).** "Welcome back. This is session {N}. Last time:
{LAST_ASSIGNMENT}. How'd it go?" Then arc-level reflection across sessions, not
just this one: "In session 1 you said 'small businesses'. Now you're saying
'Sarah at Acme'. That shift is a signal." Then the design trajectory with an
interpretation, then the accumulated signals from the profile.

Builder-to-founder nudge, only when `NUDGE_ELIGIBLE` is true: "You started this
as a side project. You've named specific users, pushed back when challenged, and
your designs keep getting sharper. I don't think this is a side project anymore."
If the evidence does not support it, skip it entirely. It has to be earned.

**inner_circle (8+).** "You've done {N} sessions and iterated {M} designs. Most
people who show this pattern end up shipping." The data speaks; no pitch. Full
accumulated signal summary.

### Founder resources (all tiers)

```bash
node ~/.claude/skills/office-hours/scripts/tb-officehours.mjs resources \
  --pick 3 --context <key> --mark
```

Context keys: `quitting-job`, `ai-product`, `idea-generation`, `not-a-founder`,
`technical-only`, `where-to-start`, `not-shipping`, `cofounder`,
`first-time-full-picture`. Omit `--context` when nothing fits; an unknown key is
refused rather than ignored.

`--mark` records the picks in the same file the dedup is read from, so the log
cannot drift from what was shown. The selector guarantees no URL is ever shown
twice and never returns three of one category while another category still has
something unseen. **Exit 3 means the pool is genuinely out — skip the section.**
Do not re-show one.

gstack asks the model to enforce all three of those rules by reading a 34-item
list in its context, and its skip rule only fires at 34 shown, so at 33 the
instruction is still "pick 2-3" and the only way to obey it is to repeat.

Present each as:

```
> **{Title}** ({duration})
> {why this one, for their situation, in 1-2 sentences}
> {url}
```

Then offer to open them:

```bash
node ~/.claude/skills/office-hours/scripts/tb-officehours.mjs link <url> [<url> ...]
```

gstack calls bare `open`, which on Windows is:

```
$ open https://ycombinator.com/apply
bash: open: command not found
```

`link` uses the platform opener (`rundll32 url.dll,FileProtocolHandler` on
Windows, `open` on macOS, `xdg-open` then `gio open` elsewhere), refuses any
scheme that is not http, https or file, and exits non-zero with the URL printed
when nothing was opened. A link that did not open is reported as not opened.

### Hand them into the loop

Do not just list options. Offer to run the next review now, mapping the doc to
the recommendation: expansive or ambitious → `/plan-ceo-review`; well scoped →
`/review`; visual or UX-heavy → `/design-review`; everything at once →
`/autoplan`. Default to `/autoplan` when it is ambiguous.

Ask once via AskUserQuestion, with the recommendation marked, then invoke the
chosen skill through the Skill tool. On a decline, stop cleanly; the design doc
is on disk and every downstream skill discovers it there.
